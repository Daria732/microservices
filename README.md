# Лабораторная работа №3
## Декомпозиция и проектирование микросервисной системы

### 1. Описание предметной области

#### 1.1. Назначение системы

Разрабатываемая система FoodFit предназначена для формирования персональных рекомендаций по питанию и физической активности с учётом индивидуальных характеристик, целей и предпочтений пользователя.

Система ориентирована на людей, которые хотят контролировать свой рацион, отслеживать физическую активность и постепенно формировать более здоровые привычки. Основная задача приложения — объединить инструменты учёта питания и активности в одном интерфейсе и предоставить пользователю персональные рекомендации на основе введённых данных.

FoodFit представляет собой мобильное приложение. Клиентская часть отвечает за взаимодействие с пользователем, отображение информации, ввод и редактирование данных, а также отправку запросов к серверной части. Серверная часть в рамках проектируемой архитектуры должна обеспечивать обработку данных, выполнение расчётов и формирование рекомендаций.

#### 1.2. Основные функции системы

К основным функциям FoodFit относятся:

- регистрация и авторизация пользователей;
- создание и редактирование персонального профиля;
- расчёт индивидуальной суточной нормы калорий и основных питательных веществ;
- ведение дневника питания с возможностью добавления продуктов и приёмов пищи;
- поиск продуктов и получение информации об их пищевой ценности;
- просмотр рецептов с указанием состава и питательных характеристик;
- учёт физической активности;
- формирование персональных рекомендаций по питанию и физической активности;
- ведение списка продуктов, имеющихся у пользователя.

#### 1.3. Основные акторы системы

В системе выделяются следующие акторы:

- **Пользователь** — основной участник системы. Заполняет профиль, указывает свои цели, ведёт дневник питания, отслеживает физическую активность и получает персональные рекомендации.
- **Внешний сервис каталога продуктов** — предоставляет сведения о продуктах и их пищевой ценности. Может использоваться для поиска продуктов при добавлении их в дневник.
- **Серверная часть FoodFit** — обрабатывает пользовательские данные, выполняет необходимые расчёты и формирует рекомендации. В рамках данной лабораторной работы её взаимодействие с мобильным приложением рассматривается на уровне проектируемой микросервисной архитектуры.

#### 1.4. Пользовательские сценарии

Основные пользовательские сценарии системы FoodFit описывают действия, которые пользователь может выполнять для контроля питания и физической активности.

1. **Регистрация и создание профиля.** Как новый пользователь, я хочу зарегистрироваться и заполнить персональный профиль, чтобы система могла учитывать мои индивидуальные характеристики при расчёте норм питания и формировании рекомендаций.

2. **Расчёт нормы питания.** Как пользователь, я хочу получить индивидуальную суточную норму калорий и питательных веществ, чтобы понимать, какое количество энергии и нутриентов мне необходимо с учётом моей цели и уровня активности.

3. **Ведение дневника питания.** Как пользователь, я хочу добавлять продукты и указывать их количество в дневнике питания, чтобы отслеживать потребление калорий, белков, жиров и углеводов.

4. **Получение персональных рекомендаций.** Как пользователь, я хочу получать рекомендации по питанию и физической активности, чтобы корректировать свои привычки в соответствии с поставленной целью.

5. **Просмотр рецептов.** Как пользователь, я хочу просматривать рецепты с информацией об ингредиентах и пищевой ценности, чтобы подбирать подходящие блюда для своего рациона.

6. **Учёт физической активности.** Как пользователь, я хочу выбирать и учитывать физические активности и тренировки, чтобы контролировать свою нагрузку и учитывать её при достижении поставленной цели.

7. **Управление запасами продуктов.** Как пользователь, я хочу вести список продуктов, имеющихся у меня дома, чтобы учитывать доступные ингредиенты при планировании питания.

### 2. Доменные события и ограниченные контексты

#### 2.1. Доменные события

В процессе анализа предметной области были выделены доменные события, отражающие основные изменения состояния системы FoodFit. События сформулированы как факты, которые уже произошли.

**Профиль пользователя:**
- `UserRegistered` — пользователь зарегистрировался в системе.
- `UserProfileCreated` — пользователь создал персональный профиль.
- `UserProfileUpdated` — пользователь изменил данные профиля.

**Продукты и запасы:**
- `ProductFound` — продукт был найден в каталоге.
- `PantryItemAdded` — продукт был добавлен в список домашних запасов.
- `PantryItemRemoved` — продукт был удалён из списка домашних запасов.

**Дневник питания:**
- `MealEntryCreated` — запись о продукте или блюде была добавлена в дневник.
- `MealEntryUpdated` — запись в дневнике была изменена.
- `MealEntryDeleted` — запись была удалена из дневника.

**Расчёт питания:**
- `NutritionNormsCalculated` — были рассчитаны индивидуальные нормы питания.
- `DailyNutritionSummaryUpdated` — были обновлены итоговые показатели питания за день.

**Физическая активность:**
- `ActivitySelected` — пользователь выбрал вид физической активности.
- `ActivityRecorded` — информация о выполненной активности была сохранена.

**Рецепты:**
- `RecipeViewed` — пользователь просмотрел рецепт.
- `RecipeSelected` — пользователь выбрал рецепт.

**Персональные рекомендации:**
- `RecommendationGenerated` — система сформировала персональные рекомендации.
- `RecommendationViewed` — пользователь просмотрел рекомендации.

#### 2.2. Ограниченные контексты и глоссарии

На основе анализа предметной области были выделены семь ограниченных контекстов. Каждый контекст отвечает за отдельную бизнес-область системы FoodFit, содержит собственные основные сущности и определяет значение используемых в нём терминов.

**1. Контекст профиля пользователя**

Отвечает за хранение и изменение персональных данных пользователя, необходимых для формирования индивидуальных рекомендаций.

Глоссарий:
- `User` — пользователь системы FoodFit.
- `UserProfile` — персональный профиль с основными характеристиками пользователя.
- `ActivityLevel` — уровень повседневной физической активности пользователя.
- `Goal` — цель пользователя: похудение, поддержание веса или набор массы.

**2. Контекст каталога продуктов и домашних запасов**

Отвечает за получение информации о продуктах, их пищевой ценности и управление списком продуктов, имеющихся у пользователя дома.

Глоссарий:
- `Product` — продукт с названием и характеристиками.
- `NutritionalValue` — информация о калорийности и содержании белков, жиров и углеводов.
- `PantryItem` — продукт, добавленный пользователем в список домашних запасов.
- `Quantity` — количество продукта, имеющегося в запасах.

**3. Контекст дневника питания**

Отвечает за ведение дневника, сохранение приёмов пищи и учёт потреблённых продуктов и блюд.

Глоссарий:
- `MealEntry` — запись о продукте или блюде, употреблённом пользователем.
- `MealType` — тип приёма пищи: завтрак, обед, ужин или перекус.
- `Serving` — количество продукта или блюда, указанное в записи дневника.
- `DailySummary` — сводная информация о питании пользователя за день.

**4. Контекст расчёта индивидуальных норм питания**

Отвечает за расчёт энергетических потребностей пользователя и определение рекомендуемого количества калорий и основных питательных веществ.

Глоссарий:
- `BMR` — базальный уровень метаболизма, то есть количество энергии, необходимое организму в состоянии покоя.
- `TDEE` — общий суточный расход энергии с учётом физической активности.
- `CalorieTarget` — индивидуальная суточная цель по калорийности.
- `MacronutrientTarget` — рекомендуемое суточное количество белков, жиров и углеводов.

**5. Контекст физической активности**

Отвечает за предоставление информации о физических упражнениях и сохранение данных о выполненной пользователем активности.

Глоссарий:
- `ActivityType` — вид физической активности или упражнения.
- `ActivityRecord` — запись о выполненной физической активности.
- `Duration` — продолжительность выполнения упражнения или тренировки.
- `EnergyExpenditure` — количество энергии, затраченной во время физической активности.

**6. Контекст рецептов**

Отвечает за хранение информации о рецептах, их ингредиентах и пищевой ценности готовых блюд.

Глоссарий:
- `Recipe` — описание блюда и способа его приготовления.
- `Ingredient` — продукт, используемый для приготовления блюда.
- `Portion` — порция готового блюда.
- `RecipeNutrition` — информация о калорийности и содержании белков, жиров и углеводов в рецепте или порции.

**7. Контекст персональных рекомендаций**

Отвечает за формирование рекомендаций по питанию и физической активности на основе информации о пользователе, его целях и текущих показателях.

Глоссарий:
- `Recommendation` — сформированная системой персональная рекомендация.
- `RecommendationReason` — причина, по которой система сформировала определённую рекомендацию.
- `RecommendationType` — категория рекомендации: питание или физическая активность.
- `RecommendationStatus` — текущее состояние рекомендации, например новая или просмотренная.

Выделенные ограниченные контексты отражают основные бизнес-возможности FoodFit. В качестве первоначальной архитектурной гипотезы каждому контексту будет соответствовать отдельный бизнес-микросервис. Такое разделение позволяет разграничить ответственность компонентов, определить владельцев данных и упростить дальнейшее проектирование взаимодействия между сервисами.

### 3. Карточки микросервисов

На основе выделенных ограниченных контекстов была спроектирована микросервисная архитектура FoodFit, состоящая из семи бизнес-сервисов. Каждый сервис отвечает за отдельную бизнес-возможность и является единственным владельцем своих основных данных. Для хранения информации каждый сервис использует собственное хранилище данных.

#### 3.1. profile-service

**Название:** `profile-service`

**Ответственность:** сервис отвечает за создание и изменение персонального профиля пользователя. Он хранит основные характеристики пользователя, необходимые для расчёта индивидуальных норм питания и формирования рекомендаций.

**Владеет данными:**
- персональные данные профиля;
- возраст, пол, рост и вес;
- уровень физической активности;
- цель пользователя;
- пользовательские предпочтения и ограничения в питании.

**Предоставляет:**
- REST API для создания, получения и изменения профиля;
- внутренний API для получения данных профиля другими сервисами;
- события `UserProfileCreated` и `UserProfileUpdated`.

**Зависит от:**
- Keycloak — для сопоставления профиля с идентификатором пользователя, прошедшего авторизацию.

Другие сервисы получают сведения о профиле через API или подписываются на события его изменения.

**Нефункциональные требования:** сервис должен обеспечивать надёжное хранение персональных данных, защиту от несанкционированного доступа и быстрое получение информации о профиле.

**Обоснование границы:** профиль выделен в отдельный сервис, поскольку содержит персональные данные, которыми должен владеть только один компонент системы. Изменение профиля не должно требовать изменения структуры данных дневника питания или каталога продуктов.

#### 3.2. food-service

**Название:** `food-service`

**Ответственность:** сервис отвечает за получение и хранение информации о продуктах, их пищевой ценности, а также за управление домашними запасами пользователя. Объединение этих функций позволяет работать с каталогом продуктов и списком запасов в рамках одной предметной области.

**Владеет данными:**
- информация о продуктах;
- калорийность и содержание белков, жиров и углеводов;
- список продуктов в домашних запасах пользователя;
- количество продуктов в запасах.

**Предоставляет:**
- REST API для поиска продуктов и получения их характеристик;
- REST API для добавления, изменения и удаления продуктов из домашних запасов;
- внутренний API для получения пищевой ценности продукта другими сервисами;
- события `PantryItemAdded` и `PantryItemRemoved`.

**Зависит от:**
- внешнего каталога Open Food Facts — для получения информации о продуктах и их пищевой ценности.

**Нефункциональные требования:** сервис должен обеспечивать быстрый поиск продуктов, поддерживать фильтрацию результатов и надёжно сохранять изменения домашних запасов. Часто запрашиваемые сведения о продуктах могут кэшироваться.

**Обоснование границы:** каталог продуктов и домашние запасы объединены, поскольку управление запасами непосредственно связано с информацией о продуктах. Такое решение позволяет избежать излишнего дробления системы и уменьшить количество взаимодействий между сервисами.

#### 3.3. diary-service

**Название:** `diary-service`

**Ответственность:** сервис отвечает за ведение дневника питания пользователя. Он сохраняет информацию о приёмах пищи, позволяет добавлять продукты и блюда, изменять и удалять записи, а также получать сводную информацию о питании за выбранный день.

**Владеет данными:**
- записи дневника питания;
- типы приёмов пищи;
- количество употреблённых продуктов и блюд;
- даты и время приёмов пищи;
- информация о пищевой ценности, зафиксированная в записи.

**Предоставляет:**
- REST API для создания, получения, изменения и удаления записей дневника;
- REST API для получения дневника за выбранную дату;
- внутренний API для получения сводных данных о питании;
- события `MealEntryCreated`, `MealEntryUpdated` и `MealEntryDeleted`.

**Зависит от:**
- `food-service` — для получения информации о продуктах и их пищевой ценности;
- `nutrition-service` — для получения рассчитанных индивидуальных норм питания при отображении показателей дневника.

**Нефункциональные требования:** сервис должен обеспечивать сохранность записей, корректный учёт количества продуктов и быстрый доступ к дневнику за выбранную дату. Операции добавления и изменения записей должны выполняться с учётом защиты от повторных запросов.

**Обоснование границы:** дневник питания является самостоятельной бизнес-возможностью с собственной логикой учёта приёмов пищи. Его данные часто изменяются пользователем и не должны напрямую храниться в сервисе каталога продуктов или расчёта норм.

#### 3.4. nutrition-service

**Название:** `nutrition-service`

**Ответственность:** сервис отвечает за расчёт индивидуальных норм питания на основе характеристик пользователя, уровня активности и поставленной цели. Также он рассчитывает показатели потребления калорий и основных питательных веществ за день.

**Владеет данными:**
- результаты расчёта базального уровня метаболизма;
- общий суточный расход энергии;
- индивидуальные цели по калорийности;
- рекомендуемые нормы белков, жиров и углеводов;
- результаты расчёта суточных показателей питания.

**Предоставляет:**
- REST API для расчёта индивидуальных норм питания;
- REST API для получения рассчитанных норм;
- внутренний API для получения показателей питания другими сервисами;
- события `NutritionNormsCalculated` и `DailyNutritionSummaryUpdated`.

**Зависит от:**
- `profile-service` — для получения возраста, пола, роста, веса, уровня активности и цели пользователя;
- `diary-service` — для получения информации о потреблённых продуктах и блюдах.

**Нефункциональные требования:** расчёты должны выполняться с высокой точностью и воспроизводимостью. Сервис должен корректно обрабатывать изменение исходных данных пользователя и своевременно обновлять индивидуальные нормы.

**Обоснование границы:** расчёт энергетических потребностей и питательных норм содержит отдельную бизнес-логику и математические алгоритмы. Выделение этой функции позволяет изменять алгоритмы расчёта независимо от реализации дневника и профиля пользователя.

#### 3.5. activity-service

**Название:** `activity-service`

**Ответственность:** сервис отвечает за предоставление информации о физических упражнениях и сохранение данных о выполненной пользователем физической активности. Он позволяет просматривать доступные виды активности и вести учёт тренировок.

**Владеет данными:**
- виды физической активности;
- информация об упражнениях и разминках;
- записи о выполненных тренировках;
- продолжительность физической активности;
- рассчитанные или указанные энергозатраты.

**Предоставляет:**
- REST API для получения списка упражнений и видов активности;
- REST API для сохранения информации о выполненной тренировке;
- REST API для получения истории активности пользователя;
- событие `ActivityRecorded`.

**Зависит от:**
- `profile-service` — для получения информации о пользователе и его целях при подборе подходящей активности.

**Нефункциональные требования:** сервис должен обеспечивать быстрый доступ к каталогу упражнений, надёжное сохранение истории тренировок и возможность дальнейшего расширения списка физических активностей.

**Обоснование границы:** физическая активность представляет отдельную бизнес-область со своими данными и логикой учёта. Её выделение позволяет развивать функциональность тренировок независимо от дневника питания.

#### 3.6. recipe-service

**Название:** `recipe-service`

**Ответственность:** сервис отвечает за хранение и предоставление рецептов блюд, информации об ингредиентах, способах приготовления и пищевой ценности готовых блюд.

**Владеет данными:**
- рецепты блюд;
- списки ингредиентов;
- способы приготовления;
- количество порций;
- пищевая ценность рецептов.

**Предоставляет:**
- REST API для получения списка рецептов;
- REST API для поиска рецептов и получения подробной информации о блюде;
- REST API для получения пищевой ценности рецепта;
- внутренний API для получения информации о рецептах другими сервисами.

**Зависит от:**
- `food-service` — для получения информации о продуктах и их пищевой ценности, используемых в качестве ингредиентов.

**Нефункциональные требования:** сервис должен обеспечивать быстрый поиск рецептов, поддерживать фильтрацию и позволять получать подробную информацию о блюдах и их ингредиентах.

**Обоснование границы:** рецепты имеют собственную структуру данных и логику формирования блюд из ингредиентов. Выделение сервиса позволяет независимо расширять каталог рецептов и алгоритмы поиска блюд.

#### 3.7. recommendation-service

**Название:** `recommendation-service`

**Ответственность:** сервис отвечает за формирование персональных рекомендаций по питанию и физической активности. Для подготовки рекомендаций он использует информацию о профиле пользователя, его целях, пищевых привычках и выполненных тренировках.

**Владеет данными:**
- сформированные персональные рекомендации;
- типы рекомендаций;
- причины формирования рекомендаций;
- статусы рекомендаций.

**Предоставляет:**
- REST API для получения персональных рекомендаций пользователя;
- REST API для обновления статуса рекомендации;
- внутренний API для запуска формирования рекомендаций;
- событие `RecommendationGenerated`.

**Зависит от:**
- `profile-service` — для получения целей и персональных характеристик пользователя;
- `nutrition-service` — для получения индивидуальных норм и показателей питания;
- `diary-service` — для получения информации о пищевых привычках;
- `activity-service` — для получения информации о физической активности;
- `food-service` и `recipe-service` — для подбора продуктов и блюд с учётом потребностей пользователя.

Для уменьшения количества синхронных запросов сервис может получать изменения данных от других компонентов через брокер сообщений и поддерживать актуальные копии необходимых сведений.

**Нефункциональные требования:** сервис должен обеспечивать формирование рекомендаций на основе актуальных данных, поддерживать возможность расширения алгоритмов и сохранять результаты их работы.

**Обоснование границы:** формирование рекомендаций является отдельной бизнес-возможностью, объединяющей данные из нескольких предметных областей. Выделение сервиса позволяет независимо изменять алгоритмы персонализации и в дальнейшем подключать интеллектуальные модели.

#### 3.8. Альтернативные варианты декомпозиции

В процессе проектирования рассматривались альтернативные варианты разделения системы.

Первый вариант предполагал создание отдельного микросервиса для каталога продуктов и отдельного сервиса для домашних запасов. От этого решения отказались, поскольку обе функции тесно связаны с информацией о продуктах. Их разделение увеличило бы количество межсервисных запросов и усложнило бы работу с данными.

Второй вариант предполагал объединение дневника питания и расчёта индивидуальных норм в один сервис. Однако от него отказались, поскольку ведение дневника и математический расчёт норм имеют разную бизнес-логику. Разделение позволяет независимо развивать алгоритмы расчёта питания и функциональность учёта приёмов пищи.

Третий вариант предполагал включение формирования рекомендаций непосредственно в `nutrition-service`. Это решение было отклонено, поскольку рекомендации охватывают не только питание, но и физическую активность. Поэтому их формирование выделено в самостоятельный сервис, который использует данные нескольких компонентов системы.

Авторизация пользователей не реализуется отдельным бизнес-микросервисом FoodFit. Для неё предполагается использовать Keycloak, поддерживающий механизмы OAuth 2.0 и OpenID Connect. Мобильное приложение будет обращаться к бизнес-сервисам через единый API Gateway.

### 4. Выбор готового программного обеспечения

Для реализации микросервисной архитектуры FoodFit были выбраны технологии, обеспечивающие хранение данных, обмен сообщениями, маршрутизацию запросов и авторизацию пользователей. Выбор компонентов основан на функциональных и нефункциональных требованиях проектируемой системы.

#### 4.1. Выбранные программные компоненты

| Компонент | Какие сервисы используют | Обоснование выбора |
|---|---|---|
| **PostgreSQL** | Все семь бизнес-сервисов | Реляционная СУБД подходит для хранения структурированных данных, организации связей между сущностями и выполнения транзакций. Для каждого микросервиса предусматривается отдельная база данных. Общая база между сервисами не используется. |
| **Redis** | `food-service` | Используется для кэширования часто запрашиваемой информации о продуктах. Это позволяет уменьшить количество обращений к основной базе данных и ускорить поиск популярных продуктов. |
| **RabbitMQ** | Все сервисы, участвующие в асинхронном обмене | Брокер сообщений обеспечивает передачу событий между микросервисами без необходимости постоянного синхронного взаимодействия. Это позволяет запускать фоновые операции и обновлять данные в других сервисах. |
| **Kong API Gateway** | Мобильное приложение и все бизнес-сервисы | Выступает единой точкой входа для клиентских запросов, обеспечивает маршрутизацию запросов к нужным микросервисам, проверку доступа и ограничение частоты обращений. |
| **Keycloak** | API Gateway | Используется для авторизации и управления доступом пользователей. Поддерживает OAuth 2.0 и OpenID Connect, что позволяет не разрабатывать собственную систему авторизации. |
| **Open Food Facts API** | `food-service` | Внешний источник информации о продуктах и их пищевой ценности. Используется для получения названий продуктов, калорийности и содержания белков, жиров и углеводов. |

#### 4.2. Организация хранения данных

В качестве основной системы управления базами данных выбрана PostgreSQL. Каждый бизнес-микросервис владеет собственными данными и использует отдельную базу данных:

- `profile-service` — база данных `profile_db`, содержащая персональные данные и настройки профиля пользователя.
- `food-service` — база данных `food_db`, содержащая сведения о продуктах и домашних запасах.
- `diary-service` — база данных `diary_db`, содержащая записи о приёмах пищи.
- `nutrition-service` — база данных `nutrition_db`, содержащая результаты расчётов индивидуальных норм питания.
- `activity-service` — база данных `activity_db`, содержащая информацию об упражнениях и выполненных тренировках.
- `recipe-service` — база данных `recipe_db`, содержащая рецепты, ингредиенты и пищевую ценность блюд.
- `recommendation-service` — база данных `recommendation_db`, содержащая сформированные персональные рекомендации.

Каждый сервис самостоятельно управляет своей базой данных. Другие микросервисы не обращаются к ней напрямую, а получают необходимые сведения через API или асинхронные сообщения.

#### 4.3. Организация взаимодействия компонентов

Для синхронного взаимодействия между микросервисами используется REST API по протоколу HTTP. Такой подход позволяет получать необходимые данные непосредственно во время обработки запроса.

Для асинхронного взаимодействия используется RabbitMQ. Сервисы публикуют доменные события, а другие компоненты подписываются на интересующие их сообщения. Например, после изменения профиля пользователя событие `UserProfileUpdated` может быть передано сервису расчёта питания и сервису рекомендаций.

Для обеспечения надёжности асинхронного обмена предусматриваются:
- уникальные идентификаторы событий для предотвращения повторной обработки;
- повторная доставка сообщений при временной недоступности получателя;
- очередь сообщений, которые не удалось обработать после повторных попыток (Dead Letter Queue).

Мобильное приложение взаимодействует с серверной частью исключительно через Kong API Gateway. Прямой доступ клиента к внутренним API микросервисов не предусматривается.

Таким образом, выбранный набор программного обеспечения обеспечивает независимое хранение данных, взаимодействие между микросервисами и возможность дальнейшего расширения системы FoodFit.
